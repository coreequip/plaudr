# M2 Krypto: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Das Signaling wird Ende-zu-Ende-verschlüsselt und signiert. room_ws sieht nur noch `{v, iv, ct}`. Ein Linkinhaber kann keine Nachrichten im Namen anderer einschleusen, und ein manipulierter DTLS-Fingerprint wird abgewiesen.

**Architecture:** Das Raumgeheimnis aus dem Fragment liefert per HKDF den room_ws-Raumnamen und einen AES-GCM-Schlüssel. Jeder Client hat eine dauerhafte Ed25519-Identität in IndexedDB, `peerId` wird aus dem öffentlichen Schlüssel abgeleitet. `Signaling` signiert und versiegelt jede Nachricht, prüft eingehende nach den Regeln aus Spec §5 und reicht nur geprüfte Nutzlasten an das Mesh weiter. Senden und Empfangen laufen über je eine serielle Warteschlange, damit asynchrone Krypto die Reihenfolge nicht verändert.

**Tech Stack:** WebCrypto (HKDF, AES-GCM, Ed25519, SHA-256), IndexedDB, Web Locks, Vitest (Node 26 mit WebCrypto), Playwright.

**Spec:** `docs/spec.md` (§3 Räume, §4 Identität, §5 Signaling, §10 M2, §11 Tests)

## Global Constraints

- HKDF-SHA-256, Salt leer; `roomId = hex(HKDF(S, info="plaudr/v1/room-id", 32 Byte))`, `roomKey = HKDF(S, info="plaudr/v1/room-key")` als AES-256-GCM-Schlüssel.
- Umschlag auf dem Draht: `{ "v": 1, "iv": <12 Byte>, "ct": <AES-GCM(roomKey)> }`; Klartext im `ct`: `{ "p": "<JSON-String der Nutzlast>", "sig": "<Ed25519(privKey, UTF-8(p))>" }`. Signiert wird der unveränderte String `p`.
- Alle Binärwerte (iv, ct, sig, pub, nonce) als base64url ohne Padding (`src/util/base64url.ts`).
- Nutzlast: `{kind, from, to, cid, ts, nonce, body}`, `nonce` 16 Byte; `hello.body = {pub, name, caps}`.
- Prüfregeln in dieser Reihenfolge: entschlüsseln, `to`, Signatur (Schlüssel aus `hello.body.pub`, `from` muss dazu passen), `|now − ts| ≤ 120 s` und Nonce neu, `cid` gleich room_ws-Absender.
- Ed25519-Privatschlüssel **nicht exportierbar**, abgelegt in IndexedDB; `navigator.storage.persist()` anfordern.
- `peerId = base32(SHA-256(publicKeyRaw))[0..26]` (RFC 4648, Kleinbuchstaben, ohne Padding).
- `setRemoteDescription` nur für Nachrichten, deren Signatur geprüft ist.
- UI-Texte deutsch, duzen, keine Gedankenstriche.
- Commits: eine Zeile, Deutsch, Aussageform, direkt auf `main`.

## Review Focus

1. **Asynchrone Krypto ändert die Reihenfolge:** offer vor ice, hello vor offer müssen in Sende- und Empfangsreihenfolge bleiben (Task 3, Tests „Reihenfolge“).
2. **Senden während eines Signaling-Ausfalls:** Nachrichten tragen nach dem Reconnect die neue cid, statt beim Empfänger an Regel 5 zu scheitern (Task 3, Test „hält Nachrichten bis zum nächsten members zurück“; erledigt Review-Minor M5 aus M1).
3. **Derselbe Browser in zwei Tabs:** Beide hätten dieselbe Identität und damit dieselbe peerId; der zweite Tab muss das erkennen und nicht beitreten (Task 4, E2E „zweiter Tab“).
4. **IndexedDB nicht nutzbar** (privater Modus, blockierter Speicher): Beitritt muss trotzdem gehen, mit flüchtiger Identität und Hinweis (Task 2, Test „Speicher schlägt fehl“).
5. **Eingeschleuste Nachrichten eines Linkinhabers:** gefälschtes offer mit fremdem `from`, gefälschtes hello mit fremder peerId, manipulierte Nutzlast mit Originalsignatur (Task 3 Unit, Task 4 E2E).

Empfangen (jeweils `stats()` prüfen):
- gültiges hello von B → zugestellt, `accepted === 1`.
- offer von B nach seinem hello → zugestellt.
- „Reihenfolge beim Empfangen“: hello und offer von B im selben Takt emittieren (ohne await dazwischen) → beide zugestellt, in dieser Reihenfolge.
- offer von C ohne vorheriges hello → `rejected['unknown-key'] === 1`.
- „gefälschtes offer“: C hat hello geschickt; C schickt offer mit `from = B.peerId`, signiert mit C → `rejected.signature === 1`, nicht zugestellt.
- „manipulierte Nutzlast mit Originalsignatur“: B signiert ein offer, danach wird in `p` der Fingerprint ersetzt (`tamper`) → `rejected.signature === 1`.
- „hello mit fremder peerId“: C schickt hello mit `from = B.peerId` und `pub = C.pub` → `rejected.identity === 1`; danach ein echtes offer von B wird weiterhin als `unknown-key` abgewiesen (falscher Schlüssel wurde nicht gemerkt).
- falscher Raumschlüssel → `decrypt`; `{v:0,p:{…}}` → `decrypt`; ct mit gültigem Umschlag, aber Klartext kein JSON oder ohne `sig` → `malformed`.
- `to` fremde peerId → `to`; `ts` 121 s alt → `replay`; gleiche Nonce zweimal → zweites `replay`; `cid` passt nicht zum Absender → `cid`.
- Nonce-Cache wird nach 240 s geleert (bestehender Test, angepasst).
